## Oryx 第四轮：前端拆 ES Module

目标：把 9705 行的前端单文件拆成 ES Module，让「改一处怕崩一片」变成
「依赖显式可见」。范围：S1 静态资源分发层 + S2 前端拆分 + 强验证。

### 关键结论
- `index.html` 9705 行 → **169 行**（只剩壳）；CSS 2746 行独立；JS 6791 行
  拆成 **22 个 ES Module**（`core/web/modules/`），仍零构建、零依赖。
- 新增 `GET /web/{path}` 静态资源路由（`server.py`），路径穿越 6 种变体全部 403。
- 令牌注入点从 index.html 移到 core.js，所以 `/web/*.js` 也要做占位符替换。
- 新增 4 个验证脚本：`check_web_modules.py`（import/export + 无环 + 真实加载）、
  `check_web_functional.py`（真点按钮的功能回归）、改造 `check_web_script.py`、
  改造 `check_web_syntax.py`（逐模块 Chrome 编译）。

### 重要教训（务必记住）

1. **ES Module 成环 = 页面白屏。**
   依赖分析发现分区之间有 **21 个循环依赖环**（UI 事件处理天然双向：
   点按钮 → 渲染 → 列表项再响应点击）。原建议里「用 import/export 互相引用」
   在这个代码库上会直接 TDZ 白屏。
   破环只能靠**合并模块**，不能靠「把符号下沉到共同祖先」——
   下沉会造出**新**环（tlAgentStarted 下沉到 core 后 core↔agui 成环）。
   代价：15 个分区被合并，最大两个文件约 1400 行。

2. **建依赖图要用有向图。**
   一开始建成无向图（h↔oh），把「谁用谁」的信息丢了，
   于是 core↔boot 这种假环也冒出来，合并算法跟着跑偏。

3. **merge_map 必须链式解析。**
   合并是递进的：checkpoint→workflow，后来 workflow→chips。
   只查一层会拿到中间名，符号留在一个不存在的模块里。

4. **`--dump-dom` 在有 EventSource 长连接的页面上会永远挂起。**
   `--dump-dom` / `--screenshot` 都等「页面静止」，SSE 长连接让它等不到。
   真实加载检查必须走 **CDP**（订阅 Runtime.exceptionThrown / consoleAPICalled）。
   本机只有 Edge 可用（Chrome 路径不存在）。

5. **CDP 里 `Runtime.evaluate` 的 id 必须全局唯一。**
   硬编码 id=1 会与 Page.enable 撞号，收不到响应（返回 None）。

6. **module scope fixture 会泄漏环境变量 —— 这是我自己引入的回归。**
   test_security.py 改成 module scope 解决「19 次重建服务导致卡死」后，
   环境变量用 os.environ 直接设（module scope 下 monkeypatch 只活到函数结束），
   ORYX_HOME 泄漏到后续测试 → test_semantic / test_toolindex 等十几个用例
   莫名全挂。**必须用 pytest.MonkeyPatch 上下文自己管并在 finally 里 undo**，
   sys.modules 的增删也要还原。
   教训：单跑全绿 + 全量全挂 = 跨用例污染，往「改了 fixture scope」方向查。

7. **正则里的 `\b` 对非单词字符无效。**
   符号名可能是 `$` / `$$`，`\b` 在非单词字符后匹配不到边界，
   export 会**静默加不上**。要用 `(?![A-Za-z0-9_$])`。

8. **改测试断言时不能只改文件路径。**
   前端拆开后 `read_text("index.html")` 只能看到壳 ——
   断言「某个函数/选择器还在」会全部失效。
   要用 `tests/webread.py` 的 `page_source()`（页面 + 全部模块 + 全部样式）。

## Oryx 第五轮：系统提示词外置

目标：把 `loop.py` 里 5950 字符的系统提示常量搬到 md 文件，

### 关键结论

  `raw_system_prompt()` 保留占位符（给模块级常量用），`lru_cache` 缓存读盘。

  `tests/fixtures/system_prompt_baseline.txt` + 对比测试钉死。
- 全量 **967 passed / 0 failed / 11 skipped**；既有 `test_prompt_contract.py`
  29 条断言一条没改。

### 重要教训（新增）

1. **提示词外置必须先有「逐字节等价」的锚点。**
   提示词差一个空格都可能让模型行为变样，而且这种变化极难归因。
   所以切分要用**脚本**（`scripts/extract_system_prompt.py`），不能手工复制 ——
   手工复制 175 行必然漏空格，而这种错误很难发现。

2. **原文里可能有「没有标题行的开篇段落」。**
   第一次切分时 `# 一、` 之前那段引言被漏掉，脚本自查报「首个差异在第 0 字符」。
   切分脚本必须能处理「第一段没有标记行」的情况。

3. **外置后，原文载体没了，切分脚本要改读基准快照。**
   否则脚本第二次运行就找不到源。

4. **占位符缺失必须报错。**
   把 `{agents}` 原样送到模型面前，模型会把字面量当内容读 —— 极难查的行为漂移。

5. **动态片段不能外置。**
   Agent 清单 / 技能目录 / 专家 / 长期记忆规则都由目录与用户数据运行时生成，
   放成静态文件反而会过期。

## 2026-11-09：第五轮验证期的事故复盘与收尾

### 验证结果
- 全量 **967 passed / 0 failed**（多轮），高负载下也是。
- 提示词专项 46 passed（新增 2 条诊断开关测试）。
- A/B 对照实验：正常 0/40 失败、LEGACY 0/40 失败（两边同样不复现）。

### 查清的两件事

**1. `test_domains` 偶发失败（no such table: tasks）—— 已修**
- 根因：`tests/conftest.py` 的 `_TEST_HOME` 是**固定路径**
  `%TEMP%/oryx-test-home`，atexit 无条件 `rmtree` 整个目录。
  两个 pytest 进程并发时，后者的 atexit 删掉前者正在用的 oryx.db。
- 修法：目录名带 pid（`oryx-test-home-{pid}`）+ atexit 只删自己那份 +
  陈旧目录下次启动清理（`_purge_stale_dirs`）。
- 对照实验已验证：旧版「A 的 db 被 B 删掉」，新版「A 不受影响」。

**2. `test_context_resume` 偶发失败（历史摘要不在 system 里）—— 已加固断言**
- 频率：约 1/12 次全量，只在高负载下。
- **穷举 768 种组合**证明：「裁剪事件发了」与「摘要含『历史摘要』」
  在 `trim_history` 逻辑上**必然同时成立** —— 静态分析排除了所有代码路径。
- 处理：断言从「`systems[0]` 含摘要」改成「**至少有一次**含摘要」，
  并打印诊断信息。**强度已验证**（故意破坏注入逻辑后仍失败）。
- 判定与提示词外置**无关**：外置只改 system 的来源，内容逐字节相同。

### 重要教训（工具类，都差点造成真损坏）

1. **BOM 被写成正文**：`read_text("utf-8")` 读带 BOM 的文件 →
   BOM 变成正文里的 `U+FEFF` → 写回后文件「能跑但很脏」。
   正确：先 `read_bytes()` 看前 3 字节是不是 `efbbbf`，按 `utf-8-sig` 读写。
2. **CRLF 被改成 LF**：`read_bytes().decode()` **不做**换行转换 ——
   锚点用 `\n` 匹配不上 CRLF 文件；反过来用 `\n` 写回就把整个文件行尾改了。
   `oryx/loop.py` 是 **UTF-8 BOM + CRLF**，改它必须两个都保。
3. **文件级脚本要自检**：改完任何文件都该验证「编码 + 行尾 + 语法」，
   而不是只看内容对不对 —— 我差点把损坏当正常。

## 2026-11-09：第九轮 —— 工具检索修中文 + mutates 声明复核

### 本轮目标
上一轮结尾提的：「扩展工具进语义索引」+「mutates 清单纳入校验」。

### 实际发现：扩展工具**本来就在**索引里
`tool_index.ensure(self.registry)` 传的是完整 registry，扩展工具已在里面。
所以「进索引」不需要改代码 —— 真正的问题是**检索本身召回不了**。

### 修掉的三个真问题

**1. 中文查询搜不到工具（影响所有工具，不只扩展）**
关键词路 `needle.split()` —— 中文没空格，「统计字数」整句一个 token，
`in` 描述里的「统计文本里的字数」不连续 → 匹配不上。
与第六轮技能路由同类毛病。改用 `registry.tokenize()`（bigram，带 LRU 缓存），
并区分信号强度（名 +6 / 描述 +3 / 语义 +1）。

**2. 索引构建失败时没清空旧索引**
`ensure()` 在 `_build` 失败时只置 `_loaded=False`，**没清 `_matrix`** →
`search()` 拿上次成功的**过期矩阵**返回结果。工具集早变了，检索还在按老数据排。
现在失败时清空三个字段；`search()` 在 `not loaded` 时返回空。

**3. 无关查询乱召回**
「zzzqqqxyz」所有工具余弦分 0.35-0.40（平顶无区分度），真查询 0.57 明显更高。
→ **关键词 0 命中时语义阈值提高**（0.25 → 0.45）。噪音 6 条 → 0 条。

### mutates 复核：第一版 100% 误报
子串匹配翻车：`kill`∈`use_skill`、`put`∈`input`、`set`∈`settings`、`run`∈`runs`。
**误报率 100% 的检查比没有检查更糟**（用户会养成忽略它的习惯）。
改成按 `_` 分词比对**完整词** → 当前 80 个工具 0 误报，
且 `fs_write`/`term_run`/`browser_click` 照样能抓出来。

### 教训
1. **先验证「是不是本来就在」** —— 我以为扩展工具要单独接索引，
   实际早就在 registry 里了。**先查清再动手**。
2. **误报率 100% 的检查等于没有检查** —— 启发式必须先在自己代码上跑一遍，
   逐条核实。核实 5 个可疑项全是误报，才动手改匹配方式。
3. **启发式要分词后比对完整词**，别用子串。

## 2026-11-10：第十一轮 —— 前端扩展的样式隔离 + 事件总线

### 本轮目标
上一轮结尾提的：样式隔离 + 核心接事件总线（让前端扩展真正「敢用」）。

### 落地
- **Shadow DOM 隔离** —— `uiext.js` 造宿主 div → attachShadow →
  扩展的 DOM 与 `<style>` 都在里面。`ctx.addStyle(css)` 注入样式。
- **CSS 变量照常继承** —— 关键发现：自定义属性是**继承**的，
  不依赖选择器匹配。变量定义在 html 上 → 继承到 shadow host → 进 shadow root。
  **所以隔离是白拿的，不需要额外桥接**；暗色主题也自动跟随。
- **事件总线放 core.js** —— core.js 是依赖根，不 import 业务模块。
  扩展与核心 import 同一 URL 的 core.js → 浏览器模块缓存 → 同一实例。
  放别处（uiext.js）就会变成两套监听器，谁也收不到谁的事件。
- **核心 emit** —— `setView` → `view:changed`；`refreshState` → `state:changed`；
  `openSession` → `session:changed`；`applyTheme` → `theme:changed`；
  扩展加载完 → `uiext:ready`。
- **核心收** —— boot.js 里接 `ui:view` / `ui:session` / `ui:toast`。
  接线放 boot.js 是因为它是「谁负责响应」的天然位置，
  不用让 core.js 去 import 业务模块（要保持依赖根）。
- **验证扩到 14 项** —— 加了隔离与双向总线的断言。

### 一个检测坑（重要）
判断「核心样式是否渗进扩展」时：
- 不能只看「高度 > 5」—— **浏览器默认的 `<button>` 本来就有 21px 高**，恒为真
- 不能用 `.iconbtn` —— 扩展自己就定义了它，测的是扩展的 CSS
- 正确做法：用**核心独有的类名**（`.navitem`）在 shadow root 里放元素，
  跟普通 div 比 computed style，有差异才说明渗入

### 另一个顺序坑
「面板内容来自后端」这项要先取值再切视图 ——
view:changed 事件会把那段文字覆盖掉。检查顺序错了会误报。

### 验证
- 全量 **1085 passed / 0 failed**（本轮纯前端，Python 测试数不变）
- 前端扩展真实浏览器验证 14 项全过
- 前端四项全过（含**依赖图无环** —— uiext.js → core.js 没成环）

### 边界（下一轮）
- 扩展的 CSS 进 shadow root 后，**核心的类名用不了**（`.iconbtn` 等）——
  要么扩展自己写，要么提供一个「核心样式子集」注入
- 扩展**不能直接操作核心 DOM**（shadow root 挡住了）——
  要操作核心界面只能走事件（ui:view 等），这是设计取舍

## 2026-11-10：第十二轮 —— 核心样式子集 + 扩展热重载

### 本轮目标
上一轮结尾提的：核心样式子集注入 + 扩展热重载。

### 落地
- **新增 `core/oryx/uicss.py`** —— 核心 CSS 子集提取器（手写扫描器，零依赖）。
  - `GET /api/ui/base-css?classes=btn,inp` → 只给这些类的规则
  - `GET /api/ui/core-classes` → 核心 411 个类名清单
  - 扩展清单加 `baseCss: ["btn", "inp"]`
  - 核心子集**先注入**、扩展样式**后注入**（扩展能覆盖核心）
- **热重载** —— 扩展 URL 带**内容指纹**（index.js + oryx.json 的 hash）；
  清单接口 `Cache-Control: no-store`；前端 5 秒轮询比对指纹；
  变了就卸载重挂。`ctx.onCleanup(fn)` 给扩展清理全局监听器用。

- **`tests/test_uicss.py`** —— 12 个 CSS 提取单元测试。

### 两个 CSS 提取的实现坑
1. **@media 里要连选择器一起保留** —— 只留声明体会变成
   `@media (...) { font-size: 11px }`，那是**无效 CSS**，浏览器整块丢弃。
2. **@media 块的类集合要是内部规则的并集** —— 否则「这块涉及哪些类」永远空集，
   **里面的规则一条都提不出来**。

### 一个验证设计的坑（重要）
热重载验证我一开始开了**两个浏览器会话** —— 第二个会话是新页面，
会直接加载最新代码。**那测的是「浏览器缓存没命中」，不是热重载。**
热重载的定义是**同一个页面**里代码被换掉。
正确做法：一个 CDP 会话，页面在等「版本 B」，
Python 侧在 `on_send` 回调里改文件（发出求值请求后、等响应前改）。

### 效果
- `.btn` 子集 1,611 字节 vs 核心 103,501 字节 —— **省 98%**
- 扩展里的 `.btn` 拿到核心的圆角（浏览器验证实测）

### 验证

## 2026-11-10：第十三轮 —— 后端扩展热重载 + 扩展管理界面

### 本轮目标
上一轮结尾提的：后端扩展热重载 + 扩展清单管理界面。

### 落地

  `.py`/`.json`/`.md` 的 hash。`compute_fingerprint()`。

  → 重新执行模块 → 重建 ToolSpec。

  + 加载错误 + 「重新加载」按钮。

### 两个真 bug（都是我自己的）
1. **「要不要覆盖」判断写反** —— 用 `old.fn is not new.fn`，
   扩展自己的新旧 fn 当然不同 → 每次热重载都被当「冲突」跳过 →
   **重载了但没生效**（版本 A 仍是 A）。
   正确做法：看「这个工具是不是扩展提供的」（`_uiext_owner` 标记）。
2. **`paint` 是 renderSettings 的局部函数** —— 重载回调在外部访问不到 →
   重载后表格消失。改成独立函数 `renderExtensionsInto(main)`，
   重载后**只重画这一节**（重画整页会把用户拉回第一页）。

### 设计取舍
- **完全重新执行**而不是 `importlib.reload()` —— reload 保留全局状态，
  改了代码旧状态还在，行为可能对不上。代价是模块状态归零。
- **两条安全规则始终可见** —— 「仓库扩展不自动加载」「扩展不能覆盖内置工具」
  不只在出错时显示：用户看不到就等于没有。
- **热重载不绕过信任检查** —— project 信任的扩展本来就不执行代码。

## 2026-11-10：第十五轮 —— 扩展启停/安装 + 后端热重载自动化（扩展体系闭环）

### 本轮目标
上一轮结尾提的：扩展的启停与安装 + 后端热重载自动化。

### 落地
- **新增 `core/oryx/extmanage.py`** —— 启停（配置黑名单）、安装（复制）、
  删除（移进回收区）、回收区列表/恢复/彻底删除。
- **停用名单接入注册表** —— `Registry.set_disabled()`；停用的扩展
  **不进注册表**（不被发现、不被加载）；**停用优先于 profile**。
- **新增接口** —— enable / disable / install / DELETE / trash。
- **设置页扩展节** —— 每行加启停按钮；加「安装」按钮（弹窗填路径）；

- **后端热重载自动化** —— agentd 后台监视线程，每 8 秒比对指纹。
  关掉：`ORYX_EXT_AUTORELOAD=0`。
- **`tests/test_extmanage.py`**（17 个）。

### 三条设计原则
1. **程序不改用户的扩展文件** —— 启停状态存 Oryx 自己的配置
   （`disabled_extensions`）。扩展文件是用户的东西，程序擅自改它，
   用户下次 `git diff` 会一脸问号。
2. **安装后默认禁用** —— 「装」与「让它跑」是两个独立决定。
   扩展是在你的机器上执行代码的东西。
3. **删除是移进回收区** —— 误删能找回。回收区在 `extensions/.trash/`。

### 安全细节
- **安装时不执行源目录的任何代码**（只是复制文件）—— 有测试专门盯
- 复制失败会**收拾干净**，不留半个扩展
- 跳过 `__pycache__` / `.git` / `node_modules`
- 重名拒绝（避免悄悄覆盖）

## 2026-11-10：第十六轮 —— 界面扩展的启停与删除 + 回收区界面（两侧一致）

### 本轮目标
上一轮结尾提的：补齐界面扩展的启停与删除入口 + 回收区界面。

### 落地
- **一套停用名单管所有扩展** —— 界面扩展不再单独机制，
  与后端共用 `disabled_extensions`。用户关掉的，**两边都不加载**。
  （「一套机制管两边」比「两套各自一致」更不容易漂移）
- **两个回收区** —— `extensions/.trash/` 与 `ui-extensions/.trash/`，
  **不合并**（内容形态不同：Python vs JS），界面上用「类型」列区分。
- **界面操作补齐** —— 每行「启用/停用」+「删除」；
  顶部「安装后端扩展」+「安装界面扩展」两个按钮；回收区可恢复/彻底删除。
- **新接口** —— `DELETE /api/ui-extensions/{id}`、
  `POST /api/ui-extensions/install`、
  `POST /api/extensions/trash/restore`、
  `POST /api/extensions/trash/purge`、
  `GET /api/extensions/trash`（合并两个回收区，带 kind 字段）。
- **设置页扩展节** —— 回收区折叠区；删除/恢复/彻底删除的委托处理。

### 三个坑（都是我自己的）
1. **`reloadExts` 是局部函数** —— 定义在 `renderExtensionsInto` 里，
   但事件委托在 `renderSettings` 的作用域，访问不到 →
   `reloadExts is not defined`。跟上一轮 `paint` 是**同一类**。
   **修法**：提到模块级 `reloadExtensionsSection(main)`。
   **教训**：跨作用域共享的回调必须模块级。
2. **CDP evaluate 访问不到模块作用域的变量** —— `S`、`api` 是
   ES Module 导出，**不是 window 属性** → `api is not defined`。
   只能用 DOM 或页面里的 fetch。
3. **启停是持久的，污染后续测试** —— 写进 config.json，
   同一次运行里后面的用例看到的是**被改过**的状态。
   修法：启停用例**点两次**（第二次恢复原状）。
