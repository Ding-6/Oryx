# 工作流编排 · 前端接入

## Context

第四批已在 Python 侧落地工作流编排引擎（`core/oryx/workflow.py` + `workflow_run`/`workflow_status`/`workflow_cancel` 三个工具 + `agentd` 四个 RPC + `/api/workflows/*` 五个路由 + `workflow.*` 六类 SSE 事件），但**前端一行都没接**——目前事件发出来没人收，接口调了也没界面。

用户看到的是一个"能跑但看不见"的功能：模型在对话里调 `workflow_run` 时，用户只看到工具卡闪一下，然后几分钟后收到一大段汇总文字。中间那几十个子 Agent 在干什么、哪个阶段、哪个失败了、耗时多久，全都看不到。这跟 WorkBuddy 的 `/workflows` 进度视图差着一整层体验。

目标：把编排过程变成**可看、可查、可中止**的一等公民视图，落在左栏导航，形态对齐现有的「自动任务」页（同样是"后台跑一批东西 + 列表 + 详情"）。

前端是单文件 [core/web/index.html](file:///d:/项目/Oryx/core/web/index.html)（227KB，无构建步骤，vanilla JS + 内联 CSS），所有既有模式都要复用，不引入任何框架或依赖。

## 关键约束（复用既有模式，不新造轮子）

| 要做的事 | 复用什么 |
|---|---|
| 视图页 | [pageShell(title, lead, body)](file:///d:/项目/Oryx/core/web/index.html#L3153) — 已有页头 + 返回按钮 |
| 列表表格 | `table.mx` + `.badge` + `.kbd` + `.empty` CSS 类 |
| 左栏入口 | `.navitem[data-view]` + `#autoCnt` 计数徽标（同 `automations`） |
| 请求 | `api(path, opts)`（已自动带 `X-Oryx-Token` + `X-Oryx-Request`） |
| 转义 | `esc()` — 所有插值必须过它 |
| 弹层 | `openModal({title, body, foot, wide})` |
| 提示 | `toast(t)` |
| SSE | [handle(ev)](file:///d:/项目/Oryx/core/web/index.html#L2711) 的 `switch` 加 case |
| 中文映射 | `TOOL_CN` / `AGENT_CN` / `cnAgent()` |
| 脏 HTML 防护 | 全站唯一的 `md()` 先转义再变换，编排摘要走 `esc()` 即可 |

**SSE 有两处坑必须绕开**（[handle() 顶部](file:///d:/项目/Oryx/core/web/index.html#L2711)）：
- `workflow.step.finished` 的 `summary` 可能含子 Agent 输出里的 `<`/`&` —— 一律 `esc()`
- 事件带 `seq`，断线重连会补发。`handle()` 里已有 `seq <= lastSeq` 的丢弃逻辑，**不要绕过它自己维护一套流状态**；但视图重绘要走增量（改单个 step 行的 class），不要整页 `innerHTML=`，否则补发会把用户正在看的内容刷掉

## 实施

### 1. 后端补两个缺口（前置依赖）

前端要展示"阶段 → step"树形结构，但当前 `workflow.status` 只返回**扁平**的 step 列表（`store.workflow_steps` 按 `created_at` 排序）。阶段名在 step 上（`stage` 字段），够用，但缺两样：

- **`workflow.status` 返回 run 的 `stages` 元信息** —— 目前只有 `WorkflowRun.to_dict()`（仅活动 run 有）才带 `stages`，落库的 run 查回来没有。前端要按阶段分组渲染，得从 step 的 `stage` 字段自行归组（**不改后端也能做**）
- **`store.get_workflow_run` 的 step 输出可能很大** —— 单个 step 全文进 JSON 会撑爆响应。`workflow_steps` 返回含 `output` 全文；前端列表页不该拉这些

**结论：先不改后端**。前端只拉 `run_id` + `status` + 计数做列表，点进详情才拉单 run 的完整 step（`/api/workflows/{run_id}`）。若实测某个 step 的 `output` 过长再回来加 `?brief=1`。

### 2. 左栏加「工作流」入口

[index.html L1741](file:///d:/项目/Oryx/core/web/index.html#L1741) 的 `.nav` 里，在「自动任务」后插一项：

```html
<div class="navitem" role="tab" tabindex="0" aria-selected="false" data-view="workflows">
  <svg class="ic" aria-hidden="true" viewBox="0 0 24 24">…</svg>工作流<span class="cnt" id="wfCnt"></span>
</div>
```

图标用 WorkBuddy 风格的"分叉汇聚"路径。`#wfCnt` 显示**正在跑的 run 数**（`status === 'running'`），无活动时留空（与 `#autoCnt` 显示总数的行为不同——工作流跑一次几分钟，运行中才是用户需要知道的信息）。

### 3. 视图挂载

- `setView()`（[L1979](file:///d:/项目/Oryx/core/web/index.html#L1979)）加一行 `if (v === 'workflows') renderWorkflows();`
- `VIEW_NAME`（[L3152](file:///d:/项目/Oryx/core/web/index.html#L3152)）补 `workflows: '工作流'`
- **状态隔离**：新增 `S.wf = { runs: [], activeRun: null, openRun: '', filter: 'all' }`。这是右栏 `S.teamBusy` / `S.localView` 那种"每个视图各记一份"的既有约定（见 [L3745-L3748](file:///d:/项目/Oryx/core/web/index.html#L3745)）——切走再切回不能丢状态

### 4. `renderWorkflows()` —— 列表页

`pageShell('工作流', '多 Agent 编排 —— 阶段化推进，中间结果隔离', ...)`，两段：

**上半 · 运行中（有活动 run 时才出现）**
一个卡片，标题旁 `中止` 按钮（调 `POST /api/workflows/{id}/cancel`），下面按阶段实时刷新的 step 行。状态行 `badge`：`run`(执行中) / `done`(完成) / `failed`(失败) / `skipped`(未执行)。

**下半 · 历史 run**
`table.mx`，列：名称 / 状态 / 阶段数 / step 进度（`3/5`）/ 耗时 / 时间。行可点开详情（`openWorkflowDetail(run_id)`，走 `openModal` wide）。空态用 `.empty`，文案点明触发方式（"在对话里说「用工作流跑这个」即可"）。

### 5. `openWorkflowDetail(run_id)` —— 详情弹层

`openModal({wide: true})`：
- 头部：run 状态 + `args`（如果有）
- **按 `stage` 分组**渲染 step：`store.workflow_steps` 返回的每条带 `stage`，前端 `Map` 归组
- 每个 step 一行：状态徽标 + `cnAgent(agent)` + step 名 + 耗时；展开后是 `goal` 与 `output`
- **step 详情懒加载**：点某行才 `GET /api/workflows/{run_id}` 拉全量并渲染该 step 的 `output`（避开上面说的响应体膨胀）

### 6. SSE 事件接入

`handle()` 的 switch 加：

```js
case 'workflow.started':    wfOnStarted(ev); break;
case 'workflow.stage.started': case 'workflow.stage.finished': wfOnStage(ev); break;
case 'workflow.step.started': case 'workflow.step.finished': wfOnStep(ev); break;
case 'workflow.finished':    wfOnFinished(ev); break;
case 'workflow.cancelling':  toast('正在中止工作流'); break;
```

**增量更新，不整页重绘**：`S.wf.activeRun` 持有内存态（`{status, stages: Map<stageName, {steps: Map<stepId, {status, summary, duration_ms}>}>}`），事件到达时只改对应 DOM 节点的 class/textContent。只有当用户**正不在** 工作流视图时，才记一个 dirty 标记，切过去时整体重拉一次。

`workflow.finished` 时：更新徽标 + toast 结果 + `loadWorkflowRuns()` 刷列表。

**关键约束**：`workflow_run` 是同步阻塞的（可能几分钟），期间 `S.busy` 一直为真，用户在对话里会看到"正在思考"。这是**符合预期的**——不要在前端伪造"后台运行已提交"的假象。当前的 `#live` 指示灯会一直亮，用户知道还在跑。

### 7. CSS

复用 `.badge.run/.done/.failed`（已有，[L672](file:///d:/项目/Oryx/core/web/index.html#L672)）。只需新增一组 `.wf*` 类做阶段分组与 step 行，风格对齐 `.member`（[L795](file:///d:/项目/Oryx/core/web/index.html#L795)）那种"左头像 + 主文本 + 右侧状态"的紧凑行。**不新增 CSS 变量**，深色主题自动跟随。

## 不做的事

- **不做可视化编排编辑器**（阶段/step 的表单化编排）—— 代价最大，且与"编排由模型决定"的既有立场冲突。第五批已补上「模板」（可复用编排存档 + 一键触发），可视化编辑器仍留待以后
- **不做斜杠命令**—— 需要命令注册表 + 解析 + 补全一整套机制，且插件的 `commands/` 目录至今未消费（见 [plugins/README.md](file:///d:/项目/Oryx/plugins/README.md)）。第五批同样未做，模板触发在工作流页一个按钮即可
- **不做阶段下钻的键盘导航**（WorkBuddy 有 `↑↓`/`Enter`/`Esc`）—— 表格行点击已够用，键盘导航是锦上添花
